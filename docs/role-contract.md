# Application and role contract

This records the implemented API boundary for the three PWAs and the planned Driver app. The published route schema is [`openapi/v1.json`](openapi/v1.json); this table adds authorization and product meaning that OpenAPI does not express. All listed operational requests require a backend session and the server-derived jurisdiction. A visible button or a role in a browser response is never the authorization decision.

| Application / role | Implemented entry and endpoints | Server permission and scope | Still required for the approved journey |
|---|---|---|---|
| Control / `dispatcher` | `/control/`; corridor read, fleet/assignee lookup, missions, route comparison and expiring baseline selection, legacy mission start/complete, assigned mission cancellation and delivery confirmation | `read_corridor_state`, `create_mission`, `view_mission` (owner), `compare_routes` in the assigned jurisdiction; assigned vehicles and drivers must be active and scoped | Verified route entitlement, mission-impact and reroute approval, independently authenticated receiver proof |
| Control / `regional_viewer` | `/control/`; corridor catalog, state, capabilities, maps and source/model read views | `read_corridor_state` in the assigned jurisdiction; no mission mutation | A read-only operational overview after verified corridor data is imported |
| Authority / `reviewer` | `/authority/`; corridor read; `GET /v1/field-reports`, `GET /v1/field-reports/{id}/history`, `POST /v1/reviews/{evidence_id}` including duplicate linking | `review_evidence` in the assigned jurisdiction | Contradictory-evidence trial and reviewer media-clearance UX |
| Authority / `district_officer` | `/authority/`; corridor read; `GET/POST /v1/status-decisions` | `publish_status` requires an active `status_authority` grant for the jurisdiction | Alerts and decision-to-mission impact |
| Authority / `system_admin` | `/authority/`; `GET /v1/admin/corridors`, `GET/POST /v1/admin/users`, `POST /v1/admin/users/{actor_id}/roles`, `GET/POST /v1/admin/vehicles`, story administration | `manage_users` in the assigned jurisdiction; no `read_corridor_state` or operational approval | Fleet deactivation and configuration/audit access that remains separate from road decisions |
| Field / `field_reporter` | `/field/`; corridor read; `POST/GET /v1/field-reports`, report media/history/clarification endpoints, assigned mission reads and legacy start/complete/GPS actions | `create_field_report`, `view_own_report`, `upload_own_media`, `submit_gps`; report ownership and mission assignment checked server-side | Physical-device offline/restart trial, alert inbox |
| Driver / `driver` | No Android app. Assigned mission list/detail, `POST /v1/missions/{id}/accept`, `/reject`, `/start`, `/positions`, `/declare-delivery` are available through the API | `view_assigned_mission` and `submit_gps` with active jurisdiction role and explicit driver assignment; a driver declaration cannot complete the mission without dispatcher confirmation | Android trip storage, reconnect trials, route-change acknowledgment, and receiver evidence |

`GET /v1/auth/session` and `POST /v1/auth/login`, `/v1/auth/logout` are shared identity endpoints. The frontend uses same-origin, HTTP-only session cookies; the backend rechecks persisted account roles, jurisdiction assignments, expiry, and revocation on requests. Tests in `tests/contracts/test_api.py` and `tests/contracts/test_login.py` cover those session boundaries. `tests/test_operations.py` covers wrong jurisdiction, wrong role, revoked assignment, invalid lifecycle transitions, and idempotent retries. A mission may separately assign a driver and field reporters. Receiving contact is omitted from mission lists and field-reporter detail, and exposed only in authorized dispatcher/driver detail. Route comparisons remain unverified baselines, not truck-safe recommendations.
