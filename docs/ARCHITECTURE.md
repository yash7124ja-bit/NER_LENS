# NER LENS backend architecture (v1)

**Status:** frozen engineering direction for the first backend implementation  
**Scope:** backend and operational data contracts only; no frontend implementation  
**Reference sources:** `SIH-26002-AI-Based-Smart-Logistics-and-Accessibility-Intelligence-Platform-for-North-Eastern-Region-NER.md` and `SIH-26002-TECH-STACK-IMPLEMENTATION-AND-VALIDATION.md`  
**Provisional geography:** Guwahati–Silchar is the working corridor hypothesis. It remains provisional until the route graph, alternatives, labels, source access and local review pass the corridor audit.

## 1. Decisions and non-goals

NER LENS is a decision-support service for essential-goods missions. It records what was observed, who reviewed it and how fresh it is; it does not certify that a road is safe.

| Decision | v1 choice |
|---|---|
| Application shape | Domain-sliced FastAPI modular monolith |
| Operational store | PostgreSQL with PostGIS; one transactional source of truth |
| Routing | GraphHopper adapter with pinned graph version and vehicle profiles |
| Ingestion | Scheduled, short-lived adapter jobs invoked by the API deployment or host scheduler |
| Risk | Baseline-first six-hour disruption-evidence probability; deterministic fallback/abstention |
| Primary IDs | Opaque UUIDv4 strings generated by the owning service or client where stated |
| Time | RFC 3339 with explicit offset at API boundary; normalize to UTC in storage |
| Client boundary | Any authenticated web/mobile client may call the API; UI implementation is not specified here |
| Working corridor | Guwahati–Silchar, pending audit; no state-wide coverage claim |

The following are explicitly excluded from v1: frontend implementation, LLM/RAG, autonomous agents, Kafka, Kubernetes, Redis, a vector database, a graph database, marketplace/payments, public turn-by-turn navigation, automatic closure from weather/model output, and a second long-running backend service for every domain. Add a component only after a measured v1 limitation or an approved partner requirement.

## 2. Runtime topology

```text
external sources                 identity provider
 IMD/GSI/CWC/SACHET/OSM/partners       OIDC
          |                              |
          v                              v
  scheduled adapter jobs  --->  FastAPI API  <--- authenticated clients
          |                         |  \
 immutable source snapshots          |   \-- GraphHopper sidecar
          |                         |
          +------------------> PostgreSQL/PostGIS
                                    |
                         protected media volume/object store
```

### v1 deployables

1. `api`: FastAPI application, domain modules, deterministic policy, risk baseline/model artifact and migrations.
2. `db`: PostgreSQL/PostGIS with encrypted backups.
3. `router`: self-hosted GraphHopper process with the approved corridor graph extract.
4. `scheduler`: host/CI scheduler invoking bounded adapter commands; jobs may run in the `api` image and exit.
5. `media`: a mounted protected volume for the prototype; use S3-compatible object storage only when deployment requires it.

There is no required queue, cache or service mesh. PostgreSQL transactions and a small idempotency table are sufficient for the expected v1 load. A future queue is justified only by measured ingestion/API contention or burst/retry volume.

### Process and trust boundaries

| Boundary | Data crossing it | Required control |
|---|---|---|
| Public/partner source → adapter job | Untrusted HTTP/files, credentials, source payloads | Egress allowlist, timeout, size limit, redirect/private-network rejection, raw hash, parser quarantine |
| Client → API | Authenticated JSON, GeoJSON, media and GPS | TLS, OIDC validation, request size/rate limits, schema validation, object authorization |
| API → GraphHopper | Route request and graph/segment exclusions | Local/private network only, pinned graph version, timeout, normalized response, no authority decisions in router |
| API → database | Domain commands and queries | Parameterized ORM/SQL, transaction boundaries, least-privilege service account, migrations |
| API → media store | Photographs and protected GPS exports | Content/type/size checks, malware scan, random key, encryption, signed scoped access |
| API → identity provider | OIDC discovery/key material | Pinned issuer/audience, key rotation handling, fail closed on invalid token |
| Operator/admin → configuration | Status policy, source cadence, alert templates | Role and jurisdiction checks, audit event, review for safety-sensitive changes |

No source, model, router or client may directly write operational status. Only the status policy command can create a status decision.

## 3. Domain modules

Modules live in one process and one database but communicate through service functions/DTOs. A module may query another module's read service; it must not update another module's tables directly.

| Module | Owns | Inputs | Outputs | Must not do |
|---|---|---|---|---|
| `identity` | Users, roles, jurisdictions, sessions and auth context mapping | OIDC claims, admin assignments | `AuthContext` | Decide routes or status |
| `corridor` | Corridor/graph versions, typed road/bridge/tunnel/approach segments, geometry and vehicle constraints | Approved graph manifests, audit corrections | Segment lookups and graph snapshot | Parse source-specific weather/hazard formats |
| `evidence` | Source snapshots, normalized evidence, provenance, freshness, review/conflicts | Adapter records, field reports, reviewer actions | Evidence queries and associations | Train models or publish status directly |
| `status` | Append-only operational status decisions and authority policy | Authorized status commands, reviewed evidence, expiry | Effective status by segment/vehicle/direction | Consume model score as authority |
| `risk` | Features, model metadata, predictions, explanations and abstentions | Evidence snapshot, corridor features | Risk DTOs and recomputation requests | Change operational status |
| `routing` | Vehicle profiles, GraphHopper calls, immutable verification policies and route-decision records | Origin/destination, mission, effective status, risk | Versioned route comparison/recommendation | Mark a segment closed or bypass authorization |
| `missions` | Cargo missions, vehicle assignment, graph pin, checkpoints and GPS observations | Dispatcher commands, device batches | Mission progress and delay facts | Ingest weather or alter status |
| `alerts` | Rules, localized reviewed templates, recipient resolution, delivery/ack state | Material status/risk/mission/source events | Alert records and delivery events | Free-form translation or safety decisions |
| `sync` | Idempotency, client sequence, media completion and conflict records | Retried client writes | Canonical replay responses and sync state | Grant business authorization |
| `audit` | Append-only actor/action/target/ before-after hashes | All material commands | Audit search and export | Be edited by domain code |

### Module command rules

- `evidence` may create evidence with `review_state=unreviewed`; it may not create `closed`.
- `status` accepts only authority-approved commands and cited evidence IDs; it appends a decision and never mutates history.
- `risk` may return `high`, `elevated`, `low` or `insufficient_evidence`; no risk result is a status transition.
- `routing` hard-excludes only active applicable status decisions and physical/legal vehicle constraints. Risk, staleness and uncertainty are scored separately.
- Every route comparison persists its request hash, alternatives/result, graph version, evidence/feature snapshot references, and immutable `RouteVerificationPolicy` ID/version so replay and restore can reconstruct the decision.
- Every route response exposes that policy ID/version alongside the graph version and verification mode.
- `missions` stores original GPS observations. Road snapping is a derived display value and never replaces the original.
- `alerts` evaluates deterministic rules against material events and reviewed templates; an alert is not an authorization.

## 4. End-to-end data flow

1. A scheduled adapter fetches a permitted source with timeout, source identifier and cadence.
2. The adapter stores the exact response/file as an immutable `source_snapshot` with retrieval metadata and SHA-256.
3. A source parser emits the common adapter record. Missing units, impossible geometry, unqualified time zones or schema drift quarantine the record.
4. Normalization creates immutable evidence while preserving the raw payload and parser version.
5. Spatial association links evidence to versioned road segments with the method, distance and validity interval.
6. The evidence module emits an affected-segment change. Risk recomputes only affected segment/horizon pairs.
7. Reviewers may accept or reject evidence. Status is changed only by a scoped `district_officer` or explicitly configured authority command. Expiry produces `unknown` unless renewed or explicitly reopened.
8. Routing requests the pinned graph and active status decisions, then scores alternatives with risk and evidence coverage.
9. A mission pins the graph version at creation. GPS batches update progress using capture time and sequence, while preserving received time.
10. Alert rules evaluate material changes, resolve recipients by role/jurisdiction/mission, render a reviewed template and record delivery/acknowledgement.
11. Every mutation writes an audit event in the same transaction as its domain effect where practical; asynchronous delivery has its own audit event.

If a feed is stale, unavailable or quarantined, the system records `source_health=stale|failed|quarantined`; it never interprets missing data as “no hazard” or “open”.

## 5. Domain semantics

### Evidence, status and risk are separate

| Concept | Values | Meaning | Authority |
|---|---|---|---|
| Evidence review | `unreviewed`, `accepted`, `rejected`, `merged`, `needs_clarification` | Quality/workflow state of a source observation | Reviewer workflow |
| Operational status | `open`, `restricted`, `closed`, `unknown` | Current asserted usability for a segment, direction and vehicle scope | Scoped `district_officer` or explicitly configured authority |
| Risk outlook | `low`, `elevated`, `high`, `insufficient_evidence` | Probability/exposure of disruption within a stated horizon | Baseline/model, labelled probabilistic |
| Source health | `healthy`, `stale`, `failed`, `quarantined` | Ability to rely on a source at decision time | Ingestion policy |

Weather, flood, landslide susceptibility and model output may raise risk or request verification. They do not close a road. A status decision must cite its authority and evidence IDs.

Evidence precedence for review is: time-bounded authority order; authorized official decision; corroborated reviewed field evidence; single reviewed field report; official hazard warning; model prediction; unreviewed report; absence of reports. Precedence guides conflict resolution; it does not delete lower-precedence evidence.

### Time semantics

Every external fact has separate fields:

- `observed_at`: when the phenomenon/report was observed by the source or device.
- `source_published_at`: when the source published it, if provided.
- `retrieved_at`: when NER LENS obtained the payload.
- `received_at`: when the API accepted a client mutation.
- `reviewed_at`: when a reviewer made a decision, if applicable.
- `valid_from` / `valid_until`: intended operational validity; never inferred from retrieval time alone.

All are stored as UTC `timestamptz` and returned as RFC 3339 UTC (`Z`). Client/device time is retained alongside server time and may be flagged `clock_suspect`; server time controls ordering of writes.

### ID semantics

- Internal IDs are opaque UUIDv4 strings. They have no business meaning and must not be generated from timestamps, coordinates or user identity.
- `RoadSegment.segment_type` is `road`, `bridge`, `tunnel`, or `approach`; each type retains direction, authority, geometry version, and applicable physical/vehicle constraints.
- `client_report_id` is a client-generated UUIDv4 retained across retries and is unique per installation/report. It is the offline dedupe key.
- `source_record_id` is the provider-stable ID; if none exists, use a content-derived ID scoped to source and parser version.
- `idempotency_key` is an opaque client string, maximum 255 bytes, scoped to actor + HTTP method + canonical path.
- `request_id` is server-generated unless a valid caller value is accepted and reissued in the response/log context.
- External IDs are strings with a source namespace and are never treated as internal IDs.

## 6. Source ingestion and risk

### Common source-adapter record

```json
{
  "source": "imd_district_warning",
  "source_record_id": "provider-id-or-content-hash",
  "observed_at": "2026-09-08T09:00:00Z",
  "source_published_at": "2026-09-08T09:15:00Z",
  "retrieved_at": "2026-09-08T09:18:22Z",
  "geometry": {"type": "Polygon", "coordinates": []},
  "payload": {},
  "units": {},
  "quality_flags": [],
  "snapshot_sha256": "64-hex",
  "parser_version": "git-sha"
}
```

Adapters are source-specific at the edge and common after normalization. They must fail closed on missing units, invalid coordinates, future observation times, ambiguous time zones, unsupported schema versions and out-of-bounds geometries. A `200` response containing old data is stale, not healthy.

The v1 risk target is `P(a verified operational disruption begins on segment s within the next 6 hours | data available at issue time)`. Physical occurrence time, source publication time, system retrieval time, and reviewer verification time remain separate. Records with an unresolved occurrence window are excluded from primary training. Start with prevalence and transparent hazard-rule baselines. A candidate model must beat the baseline on a blocked temporal test and be calibrated before operational use. Fewer than 30 independently verified positive event groups is demonstration-only. Model failure or stale critical input returns `insufficient_evidence` or an approved degraded baseline.

### Corridor and graph versioning

The route graph is a dated, checksummed artifact. Each segment has a stable internal ID plus external OSM/authority references, direction, geometry version and constraints. The provisional Guwahati–Silchar corridor must pass these gates before it becomes the active default:

1. Both candidate routes are routable on the current extract.
2. Heavy-vehicle/access/bridge constraints are reviewed.
3. Segment names map to authority references where available.
4. At least one credible alternative and positive-event/field-review path exists.
5. Data access terms and the operational reviewer are documented.

If the audit fails, keep the service corridor-configurable; do not silently promote the provisional corridor.

## 7. Routing, missions and GPS

### Routing

The GraphHopper adapter receives a graph version, vehicle profile, origin/destination and applicable hard exclusions. It returns feasible alternatives only. The API then computes a transparent score:

```text
travel_minutes
+ risk_weight * exposure_weighted_disruption_risk
+ uncertainty_weight * evidence_uncertainty
+ staleness_weight * critical_feed_staleness
+ deadline_weight * deadline_penalty
```

The response must expose each component and the evidence snapshot. A risk score cannot create a hard exclusion. If no verified feasible route exists, return `no_verified_feasible_route` with blocking constraints; do not invent an ETA. Graph changes do not alter an active mission until an operator explicitly recalculates.

### Missions

A mission has cargo class/priority, origin/destination, delivery window, vehicle profile, assigned vehicle (if any), graph version and state. States are `planned`, `active`, `paused`, `delayed`, `delivered`, `cancelled`. A mission may reference a route recommendation but does not imply the route is safe or guaranteed.

### GPS

GPS is collected only for an active, consented mission. Batches include device ID, monotonic sequence and points with capture time, accuracy, speed and optional heading. Store the original observation and received time. Out-of-order batches are accepted idempotently; impossible jumps/timestamps are flagged, not silently smoothed. A stopped or revoked device exposes last-fix age, never a current position.

## 8. Offline reports and media

The backend supports store-and-forward clients without prescribing their UI:

1. Client creates a stable `client_report_id` and sequence.
2. Metadata mutation is idempotent and returns `saved_on_server` plus review state.
3. Media uploads are separate, hash-addressed and retryable.
4. Metadata with failed media is `media_incomplete`; reviewers cannot treat the image as present.
5. Duplicate IDs replay the original canonical response; conflicting payloads return `idempotency_conflict`.
6. Conflicting reports remain separate and create a review conflict.
7. Account revocation or token expiry rejects protected sync without deleting the local report.

## 9. Alerts

Only deterministic rules create alerts. v1 triggers include: reviewed closure/restriction, material status change, high-risk threshold with sufficient evidence, mission delay/route invalidation, and critical-source staleness. Recipient selection is role-, district- and mission-scoped.

Templates are versioned and human-reviewed per locale (`en-IN`, `as-IN`; `bn-IN` only after native review). Variables are constrained to IDs, names, times, locations, status and contact instructions. No generated prose, LLM or unconstrained machine translation may issue a critical operational instruction. Dedupe keys include rule, material event, target scope, severity and template version. Acknowledgement does not suppress a newer severity or material change.

## 10. Audit, storage and invariants

### Audit

Audit events are append-only and include actor type/ID, action, target type/ID, request ID, timestamp, jurisdiction, before hash, after hash, reason and outcome. Status, route decision, model promotion, alert rule/template, reviewer action, GPS access/export and configuration changes are auditable. Do not log tokens, raw media or full precise GPS traces.

### Storage invariants

- Source snapshots, normalized evidence, status decisions, GPS observations and audit events are immutable; corrections append a superseding row.
- Status history is never updated in place. At most one effective decision applies for a segment + direction + vehicle scope at a given instant; overlapping scopes require explicit precedence.
- `valid_until > valid_from`; expiry never auto-opens a segment.
- Accepted evidence references exactly one immutable source snapshot or field-report revision.
- Every normalized evidence row has observation and retrieval times; missing source times are explicit/flagged.
- API geometries use EPSG:4326; metre calculations use an explicit projected CRS. Invalid/out-of-bounds geometry is rejected.
- `source_snapshot.sha256` is unique with source; a parser-version change may create new normalized evidence without duplicating the raw snapshot. Media SHA-256 and storage key are unique.
- `client_report_id` is unique; idempotency records are unique by actor + method + path + key.
- Mission GPS points are unique by mission + device + sequence; raw points are never overwritten by snapped points.
- A mission pins one graph version until explicit recalculation.
- Alert dedupe keys are unique for the material event/scope/template combination.
- Cross-module writes happen through service functions in a transaction; no module writes another module's tables directly.
- Sensitive mission/GPS/media rows are jurisdiction/object authorized; aggregation is the only regional-viewer exposure.

### Minimum tables

`user`, `role_assignment`, `jurisdiction`, `corridor_version`, `road_segment`, `source_snapshot`, `source_run`, `evidence`, `segment_evidence`, `status_decision`, `route_verification_policy`, `route_decision`, `risk_prediction`, `model_version`, `vehicle`, `mission`, `gps_batch`, `gps_observation`, `field_report`, `media_object`, `alert`, `alert_delivery`, `idempotency_record`, `sync_conflict`, `audit_event`.

## 11. Failure and degraded modes

| Failure | Required behavior |
|---|---|
| Source timeout/schema drift | Quarantine run, mark source failed, preserve last snapshot; no new “open” assertion |
| Critical source stale | Expose stale age; lower confidence or abstain; route may be unverified |
| GraphHopper unavailable | Return `502 upstream_unavailable`; never return an unlabelled cached route |
| Model artifact unavailable | Use transparent approved baseline or `insufficient_evidence`; record mode |
| Database unavailable | Fail writes; no “accepted” client acknowledgement; health readiness fails |
| Media scan fails | Keep report `media_incomplete`/`media_rejected`; no approval as complete |
| Identity provider unavailable | Existing token may be validated until expiry from cached keys; new auth fails closed |
| No feasible route | Return blocking constraints and escalation path; no false ETA |
| Conflicting status/evidence | Preserve all records; return conflict/freshness details; reviewer resolves |

Health endpoints are `/health/live`, `/health/ready` and `/health/sources`. Readiness requires database connectivity and migration compatibility; source health is reported separately so a feed outage does not masquerade as API health.

## 12. Observability, jobs, caching, and deployment

- Emit structured JSON logs with `request_id`, `actor_id` where lawful, `source_run_id`, `mission_id`, `model_version`, outcome, duration, and stable error code. Exclude tokens, raw media, credentials, and complete GPS traces.
- Measure request count/duration/error by route, database pool health, source age/run outcome, idempotency conflicts, quarantined media, route latency, prediction mode, alert creation/delivery, and job duration. Do not use high-cardinality coordinates or raw IDs as metric labels.
- Keep liveness, readiness, source health, and dependency diagnostics separate. A source outage may degrade decisions without making the API process dead.
- Run ingestion and maintenance as bounded Typer commands from the API image under a host or CI scheduler. Every job has a run ID, timeout, idempotent retry, recorded cutoff, and non-zero failure exit.
- Use no application cache in the first slice. PostgreSQL indexes, HTTP conditional requests, and the pinned GraphHopper graph cover the known need. Introduce caching only with a measured query or upstream-load problem and an explicit invalidation contract.
- Deploy the backend prototype with Docker Compose on one Linux host: API, PostGIS, and GraphHopper. The identity provider and optional object storage are external boundaries. A full product adds the separately owned web client.
- Terminate TLS at an approved reverse proxy, inject secrets at runtime, restrict source egress, back up the database/media metadata, and test restore. This is prototype/pilot readiness, not a government production accreditation claim.

## 13. Build order and acceptance gate

Implement in this order: migrations/invariants → source snapshot/adapter replay → evidence review/status state machine → GraphHopper route compare → mission/GPS ingest → offline field-report sync/media → deterministic alerts/audit → risk baseline/model artifact → hardening.

The first complete acceptance loop is:

`ingest evidence → calculate risk → compare routes → create mission → ingest GPS → accept field report → review → publish status → recompute route → alert → inspect audit`

The loop must run with deterministic replay fixtures, without manual database edits, and must demonstrate stale-feed, conflict, no-feasible-route and model-abstention behavior.
